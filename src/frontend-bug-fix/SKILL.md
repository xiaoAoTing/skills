# 前端 BUG 修复

基于假设驱动的工作流修复前端 BUG。按阶段顺序执行。

## 阶段一：理解问题

从用户描述中提取并整理以下信息：

- **现象**：具体出了什么问题？（报错信息、视觉异常、交互失效）
- **复现步骤**：如何触发。如果不明确，向用户确认精确步骤。
- **环境**：浏览器、设备、屏幕尺寸、网络条件（如相关）。
- **影响范围**：涉及哪个页面/组件/功能？是局部问题还是大面积问题？

使用 Grep/Glob/Read 定位相关源文件。如果描述模糊，先与用户确认理解后再继续。

## 阶段二：提出假设

基于现象和代码上下文，提出 **1-2 个最可能的假设**，按可能性排序。每个假设必须包含：

- **根因**：具体哪里出了问题，为什么。
- **置信度**：高 / 中 / 低。
- **依据**：代码或描述中支持该假设的证据。
- **验证方法**：如何确认或排除。

常见前端根因分类参考：

| 分类 | 典型表现 |
|---|---|
| 状态 / 数据流 | 数据过期、更新丢失、props 错误、竞态条件 |
| 事件处理 | 点击不触发、重复触发、事件委托问题 |
| 渲染 / 生命周期 | 内容闪烁、缺少重渲染、effect 执行时机错误 |
| CSS / 布局 | 溢出、z-index 冲突、响应式断点、优先级覆盖 |
| 异步 / 时序 | 缺少加载态、乐观更新回滚、请求顺序错乱 |
| 路由 / 导航 | 页面错误、参数丢失、守卫逻辑异常 |
| 第三方集成 | API 契约不匹配、SDK 版本问题、回调签名变更 |

将假设呈现给用户，对齐后进入阶段三。

## 阶段三：验证假设

按置信度从高到低逐一验证：

1. **阅读代码路径** — 从入口追踪到疑似故障点。
2. **检查假设** — 验证数据结构、事件绑定、CSS 层叠、异步顺序。
3. **定向日志或断点** — 仅在静态分析不足时使用。在疑似代码行加带清晰标签的 `console.log`，验证后移除。
4. **得出结论** — 用证据确认或排除。

如果最高置信度假设被排除，转向下一个。如果所有假设均不成立，回到阶段一重新审视问题——初始理解可能不完整。

## 阶段四：修复并确认

1. **最小化修复** — 只修改解决根因所需的部分。不要重构周围无关代码。
2. **验证修复** — 确认原始现象已解决。检查相邻功能是否有回归。
3. **总结汇报** — 向用户报告：
   - 根因是什么。
   - 改了什么，为什么这样改。
   - 是否有残留风险或需要关注的边界情况。

## 准则

- 不要盲目猜测。每个假设必须基于代码或描述。
- 优先读代码，而非加日志。日志是静态分析无法判断时的最后手段。
- 保持变更原子化。一个 BUG，一次修复，一个提交。
- 如果问题实际出在依赖库或后端，明确告知用户，不要在前端打补丁掩盖症状。
