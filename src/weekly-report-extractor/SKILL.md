# 周报提取指南

## 使命

从详细的周报文档中提取出精简、准确、易读的版本。

读者是团队成员和管理者，他们关心的是：做了什么、解决了什么问题、产出了什么价值。

他们不关心：用了什么技术框架、加了哪张数据库表、调了哪个 CSS 属性。

---

## 一、核心原则

### 1. 描述问题要具体，不要抽象

BUG 描述必须让读者一眼看懂「出了什么症状」。

错误示范：

> 审批流并发覆盖 BUG

正确示范：

> 审批流并发覆盖 BUG — A 和 B 同时打开同一工单，各自发起审批并通过，后操作者的数据覆盖前者，导致最终状态不一致。

读者不需要知道「读-改-写竞态条件」或「悲观锁」，他们需要知道这个问题在用户视角长什么样。

### 2. 不写废话

删除所有读者不关心的套话。

删除：

- 「已修复并关单」
- 「已完成代码修改」
- 「已通过 AI 协助定位并修复」
- 「影响平台为机构后台与营前小程序，属通用迭代」

这些是流程状态，不是工作内容。读者看到条目出现在周报里，自然知道已经处理了。

### 3. 准确第一，不确定就核实

如果原始文档中的结论存在前后矛盾或后续修正，必须采用最终结论，而不是初步结论。

例如：

初步排查认为是设计如此，后续确认是 BUG —— 周报中必须写「属于 BUG」，不能写「非 BUG，是安全设计」。

提取时如果发现结论有歧义，应该标注出来让用户确认，而不是自行判断。

### 4. 新功能和体验优化：写产出和价值，不写技术细节

错误示范：

> 新增 `approval_urges` 表，记录催促人、被催人、轮次、文案、是否发微信

正确示范：

> 审批人长时间未处理时，发起人无法主动提醒。新增「催一下」按钮，点击后对应审批人同时收到微信公众号消息和系统通知。

读者关心的是：

- 之前存在什么问题？
- 现在能做什么了？
- 谁受益？

技术实现细节（数据库表名、接口数量、动画效果）不属于精简周报。

### 5. 体验优化：必须说清楚「解决了什么问题」和「为什么要做」

错误示范：

> 截图小助手滚动速度翻倍

正确示范：

> 截图小助手 html_content 产出加速 — 公司内部其他服务需要引用截图小助手产出的 html_content 字段，此前滚动采集速度偏慢，影响下游消费时效。将滚动速度提升，html_content 可更快返回，加快整个下游流程。

每一条体验优化都应该能回答：

- 之前有什么问题？
- 为什么要改？（谁受影响、影响是什么）
- 改完之后好了多少？

### 6. 区分「做了什么」和「怎么做的」

精简周报只保留「做了什么」和「为什么做」。

「怎么做的」——用了什么框架、加了什么字段、改了哪个文件——这些属于技术评审或 PR 描述，不属于周报。

如果某条工作确实涉及重要技术决策，可以用一句话带过，但不要展开。

---

## 二、输出格式

### 分类

按工作性质分为三类：

1. **BUG 修复** — 修了什么已知问题
2. **新功能** — 新增了什么能力，解决了什么之前解决不了的问题
3. **体验优化** — 已有功能改进了什么，为什么改

### 每条工作的结构

标题（简短）— 正文（1-3 句话）

标题：让读者快速判断这条跟自己有没有关系。

正文：

- BUG 修复：描述用户视角的症状。
- 新功能：之前有什么问题 → 现在能做什么了。
- 体验优化：之前有什么痛点 → 为什么改 → 改完好了多少。

### 涉及仓库

如果周报涉及多个代码仓库，在末尾用表格汇总每个仓库涉及哪些工作项，方便追溯。

---

## 三、提取流程

1. 读取原始周报文档。
2. 逐条理解每项工作的内容。
3. 按 BUG 修复 / 新功能 / 体验优化分类。
4. 对每条工作，按上述原则重写：
   - BUG：写清症状，不写技术方案。
   - 新功能：写清问题和产出，不写实现细节。
   - 体验优化：写清痛点、原因和效果。
5. 删除所有废话和套话。
6. 检查准确性：结论是否有前后矛盾？是否采用了最终结论？
7. 汇总涉及仓库。
8. 输出精简版本。

---

## 四、避免的行为

- 不要把技术实现细节搬进精简周报。
- 不要添加原文档中没有的信息。
- 不要使用「已修复」「已完成」等流程状态词。
- 不要把初步结论当作最终结论。
- 不要为了精简而删除理解所必需的问题描述。
- 不要把体验优化写成纯技术改动，必须说明解决了什么问题。
