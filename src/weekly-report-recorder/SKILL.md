# 周报记录指南

## 使命

每次开发完成后，把「这次做了什么」总结成一条详细、准确、可追溯的记录，追加到用户的 Notion 周报文档中。

这条记录是 `weekly-report-extractor` 的原材料：extractor 负责精简，本 skill 负责**记全、记准**。宁可多记具体事实，不要只写一句概括。

---

## 一、记录流程

### 1. 确定目标文档

- 用户需要提供 Notion 周报文档的链接。如果没有提供，先询问，不要猜测或自行创建页面。
- 拿到链接后先 fetch 该页面，观察已有条目的结构（标题层级、是否按日期分组、格式惯例），新条目**沿用文档已有的组织方式**追加。

### 2. 收集本次工作的信息

信息来源，按优先级：

1. **当前会话上下文** — 刚才开发过程中讨论的需求背景、方案取舍、踩的坑。
2. **git diff / git log** — 核实实际改动范围、涉及的代码仓库（多仓库改动要逐个确认，不能漏）。
3. **向用户询问** — git 里看不到的信息（业务背景、产品决策原因、影响范围）如果会话中也没有，必须问，不要编造。

### 3. 判断工作类型

按性质分为三类，与 extractor 的分类对齐：

- **新特性** — 新增了什么能力
- **BUG 修复** — 修了什么已知问题
- **体验优化** — 已有功能改进了什么

一次改动同时涉及多类时，拆成多条记录，每条一个类型。

### 4. 按模板撰写并追加

用 Notion 的 update-page（insert_content）把记录追加到文档末尾或对应日期分组下。追加后告知用户写了什么、写到了哪里。

---

## 二、记录模板

### 新特性

```
### <特性名称>

**背景**：为什么要做这个？之前存在什么问题、谁受影响。

**产品方案**：最终采用的方案是什么，用户视角能做什么。如有被否决的备选方案及否决原因，简要记录。

**代码实现**：具体改动内容 — 涉及哪些模块/服务、关键的数据结构或接口变化、核心逻辑怎么实现的。

**涉及仓库**：列出所有改动的代码仓库。

**补充信息**（可选）：踩坑记录、测试记录、顺带优化的内容、遗留问题等，视情况补充。
```

### BUG 修复

```
### <BUG 简述>

**症状**：用户视角出了什么问题，什么操作会触发。

**根因**：问题的技术原因。如排查过程中结论有过修正，只记录最终结论。

**修复方案**：怎么修的，为什么这样修。

**涉及仓库**：列出所有改动的代码仓库。

**补充信息**（可选）：影响范围、是否需要数据修复、预防措施等。
```

### 体验优化

```
### <优化项简述>

**之前的问题**：痛点是什么，谁受影响，影响程度。

**改动内容**：具体改了什么，技术层面的实现。

**效果**：改完之后好了多少，尽量给出可对比的描述（如耗时从 X 降到 Y）。

**涉及仓库**：列出所有改动的代码仓库。

**补充信息**（可选）：视情况补充。
```

---

## 三、写作要求

1. **记具体事实，不记概括** — 「滚动采集速度从 200ms/屏 提升到 80ms/屏」优于「提升了滚动速度」。extractor 精简时依赖这些具体事实。
2. **症状和背景用用户视角写** — 技术细节归入「代码实现」，但「背景」「症状」要让非技术读者也能看懂。
3. **只记录最终结论** — 排查过程中被推翻的判断不要写进记录；如确有必要保留过程，明确标注哪个是最终结论。
4. **不写流程废话** — 「已完成开发」「已修复并关单」这类状态词没有信息量，不要写。
5. **涉及仓库必须准确** — 以 git 实际改动为准逐个核对，多仓库改动一个都不能漏，这是 extractor 末尾仓库汇总表的数据来源。
6. **不添加没发生的信息** — 不确定的内容问用户，不要为了模板完整而编造。

---

## 四、避免的行为

- 不要在用户未提供链接时自行创建新的 Notion 页面。
- 不要无视目标文档已有的格式惯例，另起一套结构。
- 不要把多个不相关的工作混在一条记录里。
- 不要省略「涉及仓库」。
- 不要把会话中没有依据的背景、数据写进记录。
